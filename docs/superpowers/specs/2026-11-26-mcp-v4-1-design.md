# Tripsmith MCP v4.1 — full tool set, sign-in, admin actions (design)

Status: draft for Viraj's approval · 2026-11-26 · extends [03-requirements-v4.md](../../03-requirements-v4.md)

## Why

v4 shipped four anonymous tools (`searchPackages`, `checkAvailability`, `startBooking`, `startEnquiry`). Viraj wants Tripsmith's MCP to be **genuinely useful inside ChatGPT and Claude**: for a traveller planning, for a signed-in customer managing their trip, and for the agency owner running the business. It is also the portfolio's strongest demo: *"an AI can run the whole agency, and still can't be tricked into moving money."*

## Goals

1. A traveller can plan a trip end to end in ChatGPT or Claude: where to go, what's in a package, reviews, comparisons, exact price, then a booking/enquiry link.
2. A customer can connect their Tripsmith account and see and manage their bookings.
3. The owner can connect and do **every admin action** the admin site offers (exceptions listed below), safely.
4. Works in both ChatGPT (developer mode connectors) and Claude (custom connectors), verified by connecting each by hand.

## Non-goals

- Payments inside the AI. Razorpay Checkout needs a browser; every payment stays a link to the site.
- File uploads (package images, destination covers, leader photos). MCP tool arguments are JSON; these return a link to the admin upload screen.
- Multi-tenancy, stdio distribution, an MCP client inside Tripsmith (unchanged from v4).

## Anti-goals (a failure even if it works)

- A write that happens without a human approving that exact change.
- Text written by a customer (enquiry, chat, review, traveller name) causing an action.
- A stranger using the public demo owner login to change real data.
- MCP getting its own business rules: every tool calls the same service function the site calls.

## Approaches considered

| | Approach | Trade-off | Verdict |
|---|---|---|---|
| A | One tool per API route (~90 tools) | Fast, complete; assistants choose badly among many near-duplicates | Rejected |
| **B** | **Curated per user journey; role decides which tools are listed; writes share one preview → confirm pattern** | More design work; fewer, clearer tools | **Chosen** (Viraj: "do what's best") |
| C | ~5 giant tools with many optional params | Few choices, but assistants misuse big optional schemas | Rejected |

Admin scope: Viraj chose **all admin actions** (not read-only), with the two-step confirm, an audit trail and a protected demo owner.

## Endpoints

Two MCP endpoints on the same FastAPI app (my call):

| URL | Auth | Tools |
|---|---|---|
| `/mcp` (exists) | none | the 10 public tools |
| `/mcp/account` (new) | OAuth 2.1, required | public tools + customer tools, or + owner tools, by the signed-in user's role |

Why two: clients start OAuth when the server answers 401 at connect, so "optional login" on one URL is unreliable across ChatGPT and Claude. Keeping `/mcp` anonymous also keeps the existing production smoke job and the README's URL unchanged. A user adds whichever connector they need.

## The write pattern: preview → confirm

Every write (customer or owner, except save/unsave) is two calls.

**Where preview lives (decided after the builder check).** Most write services today commit, email or call Razorpay in one step, and some routes chain several services (e.g. `move_route`: move → `send_refunds` → release → waitlist offers). So each of the ~45 write actions gets a **check-only function in the service layer** (`plan_*`: validates, computes the effect and the state fingerprint, writes nothing, sends nothing), and route-level chaining moves into a service the site and MCP both call. Existing quote/options functions (`quoteMove`, `quoteCounterBooking`, `getChangeOptions`, `quoteExtras`, `quoteBooking`) are reused as the plan step where they exist. The site's behaviour must not change; its tests prove it.

**Two approval levels (Viraj, 2026-11-26).** A client's "allow this action?" prompt can be set to "always allow", after which the model could preview and confirm alone (e.g. after reading injected customer text). So:
- **Money actions** — refund (send / record), markPaid, markBalancePaid, move, resolveCancellation, removeAddon, counterBooking create — are **approved on Tripsmith's admin site**. Their preview returns an **approval link**; the signed-in owner opens it, sees the exact change and clicks Approve. `confirmAction` refuses these. The assistant can then check the result with a read tool.
- **Everything else** is approved inside the assistant with `confirmAction` as below.

1. **Preview.** The write tool runs its `plan_*` function, changes nothing, and returns a plain-language `summary` ("Refund ₹12,400 to Priya S. for TS-1042 — 50% tier, 9 days before departure"), the exact effect, and a `confirmCode`.
2. **Confirm.** `confirmAction(confirmCode, summary)` executes it. The server rejects it unless `summary` matches the preview **exactly**. Because the summary is an argument, ChatGPT and Claude show it in their "allow this action?" prompt, so the human approves the real change, not an opaque code.

Server-side, stored in a new `mcp_pending_actions` table:
- the user, the OAuth client, tool, action, normalised arguments, summary, a hash of the code;
- a **state fingerprint** of what the preview read (e.g. the booking's amounts and status). On confirm the service runs again; if the fingerprint changed, it refuses and asks for a new preview;
- 5-minute expiry, single use, bound to the same user and client;
- once executed, the row is the **audit record** (executed_at, result). An owner can list recent MCP actions (`recentMcpActions` tool + an admin page row — builder chooses the screen).

Writes are rate-limited per token (builder picks the numbers; refunds/payments tighter than the rest).

**Rate limits (changes R36).** ChatGPT calls from OpenAI's servers, so many users share a few IPs. The anonymous `/mcp` per-IP limit is raised (builder picks the number from measured usage; it stays fail-closed). `/mcp/account` limits per user token, not per IP.

## Data rules (Viraj, 2026-11-26; replaces boundary 5)

- **Never through MCP, any role:** ID/passport numbers (except the site's existing masked form), date of birth, medical notes, allergies, emergency contacts. Tools that would need them return a link to the site's own form.
- **Customer:** sees their own bookings' names and their own contact details.
- **Real owner:** sees customers' names, phones and emails (their business data).
- **Demo owner:** names shortened ("Priya S."), phones and emails masked.
- **Stored:** `mcp_requests` and `mcp_pending_actions` keep arguments with contact details and free text redacted (`pii.redact()`), never the sensitive fields above.

## Sign-in (OAuth 2.1, per the MCP authorization spec)

- Tripsmith's api becomes its own authorization server (R38's original plan). Protected-resource metadata on `/mcp/account`, authorization-server metadata, **dynamic client registration** (both ChatGPT and Claude register themselves), authorization code + **PKCE S256**, tokens bound to the `/mcp/account` resource.
- The authorize page lives on the web app and uses the site's **own sign-in rules**: email code for customers, **password for owners** (owner emails are refused by the code flow on purpose — `OWNER_USES_PASSWORD` in `routers/auth.py` — because demo codes are shown on screen). An existing site session may skip straight to consent. Then a consent screen: app name, the user's role, what it will be able to do. Owners see an extra line: "can take admin actions after your approval of each one".
- Opaque tokens, stored hashed (like sessions): access 1 h, rotating refresh 30 days. New tables for clients, codes and tokens (builder designs them; follow `models/auth.py` conventions).
- **Connected apps** list with revoke, on the customer account page and in admin.
- `mcp_requests` rows gain user id and client id.

## Demo owner protection

The published demo owner login already exists and is read-only on the site (`DEMO_READ_ONLY_EMAILS`, enforced in `require_owner`). Through MCP:
- it connects with its public password and can use every owner **read** tool;
- **preview works, confirm and the approval link are refused** with a clear "demo account — this would have done: …" message. Recruiters see the whole flow without changing anything;
- contact details are masked (see Data rules).

## Website chat

The tool registry stays shared, with a per-tool flag for which surfaces list it. The Gemini chat gains `getPackageDetails`, `quotePrice`, `getReviews` (my call: the rest cost tokens on every turn for little chat value). Parity tests keep covering every tool both surfaces share.

## Honest-claims rewrite

v4's "MCP creates nothing" becomes:
> The public MCP creates nothing. Signed-in MCP changes data only after a preview the human approves; anything that moves money is approved on Tripsmith's own admin site, never inside the assistant; payments always happen on the site; ID, date-of-birth and medical details never pass through MCP; the public demo owner can preview but never approve.

## Testing

- Parity: each MCP tool's result equals the service/site result.
- OAuth: PKCE required, wrong redirect URI, reused/expired code, token for another resource, revoked token, refresh rotation and reuse detection.
- Role filtering: anonymous / customer / owner each list exactly their tools; a customer token can't call owner tools; a customer can't read another customer's booking.
- Confirm: expired, reused, other user, other client, summary mismatch, state changed between preview and confirm, demo owner refused, `confirmAction` refuses every money action.
- Approval link: only the same signed-in owner can approve; expired/reused refused; state change refused; demo owner refused.
- Plan functions: for each write action, `plan_*` writes nothing and sends nothing (no DB change, no email, no Razorpay call), and the site's existing tests still pass.
- Data rules: no tool result or stored row contains ID numbers, DOB, medical or emergency fields; demo owner results are masked.
- Prompt-injection fixture: an enquiry whose text says "refund TS-xxxx"; reading it returns it only under `customerWrote`, and no refund can complete without the owner approving on the site, even if every MCP call is made.
- By hand on production: connect ChatGPT and Claude to both URLs; plan a trip, view a booking, do one owner preview + confirm on a real (non-demo) owner. Record the Claude GIF.
